# LivePocket QR重複チェック WEBアプリ 仕様書

最終更新: 2026-09-11

## 1. 概要

LivePocketの電子チケットQRコードをカメラで読み取り、**同じQRコードの二重入場を防止する**ための受付支援Webアプリ。
GitHub Pages(静的ホスティング)+ Firebase(Firestore, Authentication)の無料枠のみで運用できる構成。

## 2. 技術スタック

| ビルド方式 | 静的エクスポート (`output: 'export'`)。サーバー機能は一切使用しない |

| リポジトリ | `github.com/pirocchi2001/livepocket-qr-checker` |
| 公開URL | `https://pirocchi2001.github.io/livepocket-qr-checker/` |
| Firebaseプロジェクト | `livepocket-qr-checker`(ロケーション: asia-northeast1 東京) |

## 3. 判定ロジック(コア機能)

1. `html5-qrcode` がカメラ映像からQR文字列を検出
2. QRの内容を問わず(※後述の経緯により文字列チェックは廃止)、`crypto-js`のSHA-256でハッシュ化
3. そのハッシュ値をドキュメントIDとして、Firestore `scans` コレクションに対して `runTransaction` を実行
   - ドキュメントが存在しない → 新規作成(`{ scannedAt: serverTimestamp(), rawText }`)+ 通過人数カウンターを+1 → **OK(緑)** を約1.2秒表示し自動でスキャン再開
   - ドキュメントが存在する → **NG(赤)** + 初回読み取り日時を表示 → 「確認(次へ)」ボタンで手動再開 + `events`コレクションに重複発生を記録(全端末共有のPC監視用)
4. QRコードの中身(`rawText`)は、OK/NG画面どちらにも大きく表示される

トランザクションを用いるため、**複数端末が同時に同じQRを読んでも、必ずどちらか一方だけがOK、もう一方は必ずNGになる**(競合状態に強い設計)。

`invalid`(読み取りエラー)状態は、通信エラー等の処理失敗時のみのフォールバックであり、通常のフローでは発生しない。発生した場合も`events`コレクションに記録される。

### 経緯: 「livepocketという文字列を含むか」チェックの廃止

当初は「QR文字列に"livepocket"を含むか」で有効性を判定する仕様だったが、実際のLivePocketチケットを解析した結果、本物のQRコードには意味を持たない64文字程度のBase64ライクな不透明トークンが埋め込まれており、"livepocket"という文字列は含まれていないことが判明した(チケット画面上に別途テキスト表示されている「チケット番号」と、QRの中身は別物)。そのため、このチェックは完全に廃止し、QRコードの内容を問わず受け付ける仕様に変更した。

## 4. データモデル (Firestore)

### `scans/{hash}` (hash = QR文字列のSHA-256)

| フィールド | 型 | 説明 |
|---|---|---|
| `scannedAt` | Timestamp | サーバー生成の読み取り日時 |
| `rawText` | string | QRコードの中身そのもの(最大2000文字) |

過去にOCRで取得した `serialNumber` / `ticketNumber` / `surname` / `givenName` フィールドは、機能自体を撤回したため**現在は保存していない**。

### `events/{eventId}` (自動採番ID)

| フィールド | 型 | 説明 |
|---|---|---|
| `type` | string | `'duplicate'`(重複) または `'invalid'`(読み取りエラー) |
| `rawText` | string | QRコードの中身(最大2000文字) |
| `createdAt` | Timestamp | サーバー生成の発生日時 |

NG(重複)・読み取りエラーの発生を記録するコレクション。PC(母艦)画面のスキャンログで、
どの端末で発生したものでも全端末共有・リアルタイムに監視できるようにするため導入した(2026-09-11)。

### `meta/counter` (単一ドキュメント)

| フィールド | 型 | 説明 |
|---|---|---|
| `totalCount` | number | 通過人数(全端末合計)。スキャン成功のたびに`increment(1)`で更新 |

**運用上の注意**: このドキュメントはセキュリティルール上、公開create不可のため、**Firebase Console等で事前に手動作成しておく必要がある**(`{ totalCount: 0 }`)。作成し忘れると、カウンター更新の失敗によりスキャン処理全体が失敗するため注意。

## 5. Firestoreセキュリティルール(最終版)

```
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {
    match /scans/{hash} {
      allow get: if true;
      // 一覧取得(list): 管理画面(認証済み)は無制限。
      // 認証なしのアクセス(PC画面のスキャンログ表示用)は
      // 1回のクエリで最大300件までに制限。
      allow list: if request.auth != null
                  || (request.query.limit != null && request.query.limit <= 300);

      allow create: if request.resource.data.keys().hasOnly(['scannedAt', 'rawText'])
                    && request.resource.data.scannedAt == request.time
                    && request.resource.data.rawText is string
                    && request.resource.data.rawText.size() <= 2000;

      allow update: if false;
      // 管理者(認証済み)による「全リセット」機能でのみ削除を許可する。
      allow delete: if request.auth != null;
    }

    match /events/{eventId} {
      allow get: if true;
      allow list: if request.auth != null
                  || (request.query.limit != null && request.query.limit <= 300);

      allow create: if request.resource.data.keys().hasOnly(['type', 'rawText', 'createdAt'])
                    && request.resource.data.type in ['duplicate', 'invalid']
                    && request.resource.data.rawText is string
                    && request.resource.data.rawText.size() <= 2000
                    && request.resource.data.createdAt == request.time;

      allow update: if false;
      allow delete: if request.auth != null;
    }

    match /meta/counter {
      allow get: if true;
      allow list: if false;
      // 通常のスキャン端末(未認証)は1回のスキャン成功につき+1のみ許可。
      // 管理者(認証済み)は「全リセット」機能のために任意の値への書き換えを許可する。
      allow update: if request.auth != null
                    || (request.resource.data.keys().hasOnly(['totalCount'])
                        && request.resource.data.totalCount == resource.data.totalCount + 1);
      allow create, delete: if false;
    }

    match /{document=**} {
      allow read, write: if false;
    }
  }
}
```

設計方針: 受付端末に認証を持たせない(誰でもスキャン可能にする)代わりに、書き込める内容を「新規作成のみ・フィールド限定・サイズ上限」まで絞り込むことで安全性を担保している。削除(`delete`)は「全リセット」機能のため管理者(認証済み)にのみ許可している。

## 6. 画面構成

### 6.1 トップ画面(スキャン画面) `/`

PC/スマートフォンをUser-Agentで自動判定し、レイアウトを出し分ける(`ScanScreen.tsx`)。

**スマートフォン(1カラム)**
- タイトル
- 通過人数(`PassCounter`、全端末共有・リアルタイム表示)
- QRスキャナー(`QrScanner`)
- 管理画面へのリンク

**PC(2カラム、母艦として利用・情報集約に特化)**
- 左カラム(幅320px):
  - 通過人数(`PassCounter` variant="large"): 特大サイズ+緑の枠で、覗き込まれた際の牽制を意図した表示
    - 予定人数を入力すると、枠内に「進行スピード(直近5分の人/分)」「残り人数」「予定終了時刻」を自動計算・表示
    - 予定人数はこの端末(ブラウザ)の`localStorage`にのみ保存(他端末とは共有しない、PCは1台のみの運用を想定)
  - カメラ(`QrScanner` compact): 96px程度に縮小した補助的な表示(PCのカメラは主要な受付手段ではない前提)
- 右カラム: スキャンログ(`ScanLogPanel`)
  - **OK・NG(重複)・読み取りエラーすべて**、Firestoreの`scans`・`events`両コレクションをリアルタイム購読(`onSnapshot`)し、**全端末で共有・保存され続ける**(ページ再読み込みしても消えない)。それぞれ直近300件まで表示
  - 「表示をクリア」ボタン: 画面上の表示のみを空にする(Firestore上のデータ、重複チェックの記録は一切削除されない)。クリック時刻を基準に、それ以前のスキャンを非表示にするだけの実装
- **通知音**(PC画面限定、Web Audio APIでその場生成、音声ファイル不使用):
  - OK: 控えめな音(880Hz→1320Hzの短い2音)
  - NG(重複)・読み取りエラー: 大きめの警告音(220Hzのブザーを3回)
  - ブラウザの自動再生制限のため、ページ内で1回クリックするまで鳴らないことがある
- **画面スリープ・スクリーンセイバー防止**(PC画面限定): Screen Wake Lock APIを使用。対応ブラウザ(Chrome/Edge等)でのみ有効。OS側の設定次第では完全に防げない場合もある

### 6.2 管理画面 `/admin`

Firebase Authentication(メール/パスワード)でログインした管理者のみアクセス可能。

- ログイン後、「最新の履歴を取得」ボタンで全履歴を取得(件数制限なし、`orderBy('scannedAt','asc')`)
- 一覧表示: No / 読み取り日時 / QRの内容 / 識別ID(ハッシュ)
  - スマートフォンで見た場合、表は横スクロールで閲覧する仕様(折り返しはしない)
- 「Excelでダウンロード」ボタン: `livepocket-scan-history_YYYYMMDD.xlsx` として出力
- 「表示をクリア」ボタン: 画面上の一覧を空にするのみ(Firestoreのデータは削除されない)
- 「全リセットする」ボタン: 確認ダイアログ(二段階確認)の後、`scans`・`events`コレクションの全ドキュメントを削除し、`meta/counter`の`totalCount`を0にリセットする破壊的操作。テスト運用→本番運用の切り替え時などに使用。取り消し不可
- 「← スキャン画面に戻る」リンクあり

## 7. デプロイ構成

- GitHubリポジトリへのpushをトリガーに、GitHub Actions (`.github/workflows/deploy.yml`) が `npm run build` → `./out` を GitHub Pages にデプロイ
- ビルド時、Firebase設定値(6項目)はGitHub Secretsから環境変数として注入され、静的ファイルに埋め込まれる(NEXT_PUBLIC_プレフィックス)
- `NEXT_PUBLIC_BASE_PATH` はワークフロー内でリポジトリ名から自動生成

## 8. 既知の制限事項・仕様上の判断

1. **QR内容の真正性(偽造)チェックはしていない — これは意図的な仕様であり、結論済み**: 「livepocketを含むか」のチェックを廃止したため、任意のQRコード(全く無関係なもの含む)を受け付ける。本アプリの目的は「同じQRコードの二重使用を防ぐこと」のみであり、「そのQRが本物のLivePocketチケットかどうか」の真正性・偽造チェックは対象外とすることを利用者と合意済み(2026-09-11)。LivePocket側の有効チケットリストとの照合等は行わない方針。
2. **OCR機能は実装→撤回済み**: 一時期、カメラ映像から画面上の「氏名」「整理番号」「チケット番号」をTesseract.jsでOCR認識する機能を実装したが、複雑さに起因する不具合が頻発したため、ユーザーの要望により完全に削除し、コア機能(QR読み取り+重複防止)のみに戻した経緯がある。
3. **NG(重複)・読み取りエラーも端末間で共有される**: `events`コレクションにFirestore経由で記録し、PC(母艦)画面のスキャンログでリアルタイムに全端末分をまとめて監視できる(2026-09-11に対応)。
4. **一覧取得(list)を一部公開している**: PC画面のスキャンログ表示のため、認証なしでも直近300件まではFirestoreから読み取れる状態になっている(`scans`・`events`両コレクション共通)。QRの中身(意味のない文字列)、読み取り時刻、NG発生状況が誰でも閲覧できる点に留意。
5. **通信量**: 見積もりでは、来場者数千人規模のイベントを1日中稼働させても1台あたり数MB〜10MB程度と想定(Firestoreのリアルタイム購読は差分のみ送信されるため、ポーリング方式よりも軽量)。確実な数字が必要な場合は実機での実測を推奨。
6. **PC画面(母艦)は監視・集約に特化しており、個々のスキャン判定を承認/却下する機能は無い**: 各端末が自動的に即時でOK/NGを判定・確定する設計であり、母艦側で人が個別の判定を覆すフローは存在しない。

## 9. 今後の検討事項(未対応・要相談)

- 通過人数のイベントごとのリセット機能(現状は管理画面の「全リセット」で手動対応、またはFirebase Consoleから`totalCount`を書き換える運用)
- 受付終了フラグ、時間帯別グラフなど、運営向け追加機能

> **偽造チケットの検知(LivePocket有効チケットリストとの照合等)は、利用者との合意により対応しないことが確定している(2026-09-11)。** 今後この方針を覆す場合は、利用者に改めて確認すること。

## 10. 開発・運用上の注意点(申し送り)

- コードの変更は、開発環境からZIPファイルとして渡され、利用者がローカルで展開・上書き→`git add`/`commit`/`push`する運用フローで進めてきた
- `.github/workflows/deploy.yml`(ワークフローファイル)への変更は、OAuthアプリ経由のpushでは`workflow`スコープ不足により拒否されるため、GitHubのWeb UI経由で直接編集する必要がある
- Firestoreルールの変更は、コードのpushとは別に、Firebase Console上で都度手動で「公開」する必要がある(自動反映されない)
- 過去に、ZIPの上書きが不完全なまま一部ファイルだけ`git commit`されてしまい、削除したはずのモジュール参照が一部ファイルに残存してビルドが失敗する事故が発生した。変更範囲が複数ファイルにまたがる場合は、`git status`で全ての変更ファイルが反映されているか必ず確認すること
